バックアップと復元

記録・写真・振り返り・大切な人・やりたいことを1つのファイルに書き出し、別の端末や再インストール後に戻す機能（1.1.0〜）。

実装済 機能ID: LR-FEAT-BACKUP 1.1.0 (11)

概要

人生アルバムはアカウントもサーバーも持たず、記録はすべて端末内にある。機種変更や削除で記録を失わないよう、 利用者が自分でファイルとして持ち出し、戻せるようにした。ファイルの置き場所（端末内・iCloud Drive・PC など）は システムのファイル画面で利用者が選ぶ。アプリが外部へ送ることはない（App Privacy の「データを収集していません」と矛盾しない）。

  • 書き出し: 設定 → バックアップ →「バックアップを書き出す」→ 保存先を選ぶ。ファイル名は LifeReview-Backup-YYYYMMDD（拡張子 .lifereviewbackup）。
  • 復元: 設定 → バックアップ →「バックアップから復元」→ ファイルを選ぶ → 件数入りの確認 →「復元」。現在のデータは置き換わる（足し合わせではない）。
  • 対象: 記録（LogEntry）・添付写真・振り返り（ReflectionSession）・大切な人（Relation）・やりたいこと（BucketItem）・プロフィール（UserProfile）。設定値（通知・画面の明るさなど）は含まない。
公開の状況: 1.0.x（公開中）にはバックアップ機能は無い。1.1.0 (11) の TestFlight で初めて入った。

利用者から見える挙動

場面表示・挙動
設定のバックアップ節「バックアップを書き出す」「バックアップから復元」の2行と、「前回の書き出し: 2026/10/24」（未実施なら「まだバックアップを書き出していません」）、説明「記録、写真、振り返り、大切な人、やりたいことを1つのファイルに保存します。復元すると現在のデータは置き換わります。」
書き出し成功保存先を選び終えた時点で「前回の書き出し」が今日の日付に変わる（保存をキャンセル・失敗したら日付は変えない）。
書き出し失敗「バックアップを作成できませんでした。」（中身を作れない）／「バックアップを書き出せませんでした。」（保存できない）
復元の確認「バックアップから復元しますか？」／「2026/10/24 に書き出したバックアップです（記録 ○件・写真 ○枚・振り返り ○件）。現在の記録、写真、振り返り、大切な人、やりたいことはこの内容に置き換わります。」。写真が欠けていれば「写真 ○枚が見つかりません。その写真は記録から外れます。」を足す。ボタンは「復元」（destructive）／「キャンセル」。
復元成功データが置き換わり、書きかけの振り返り（下書き）を消す。初回画面は出さない（onboardingCompleted = true）。
復元できないファイル「このバックアップの形式には対応していません。」／「このバックアップは壊れているため復元できません。いまの記録はそのまま残っています。」／「このファイルは復元できません。」
復元の途中で失敗「バックアップを復元できませんでした。もとのデータはそのまま残っています。」——記録も写真も復元前のまま。
記録は戻ったが写真の入れ替えが残った「記録は復元しました。写真の入れ替えが終わっていないため、アプリを開き直すと写真が表示されます。」——次の起動で入れ替えを済ませる。

└── photos/

    └── …
項目内容
型UTType com.happyboy1002.LifeReview.backup（project.yml の UTExportedTypeDeclarations）・拡張子 lifereviewbackup
manifest の中身version（= 2）・exportedAt・profiles・logs・relations・bucketItems・reflections。各要素は SwiftData モデルの全項目（id を含む）を写したもの。写真は logs[].imagePaths にファイル名だけを持つ

処理フロー

書き出し

sequenceDiagram participant U as 利用者 participant V as BackupSettingsSection participant B as BackupService participant D as BackupPackageDocument U->>V: 「バックアップを書き出す」 V->>B: makeManifest(context:)（5モデルを fetch） B-->>V: BackupManifest（version 2） V->>D: manifest.json の Data ＋ 写真名の一覧 V->>U: fileExporter（保存先を選ぶ） D->>D: fileWrapper: 写真は FileWrapper(url:) で遅延読み出し alt 保存できた V->>V: lastBackupTimestamp = 今 else 失敗 V-->>U: 「バックアップを書き出せませんでした。」 end

復元

sequenceDiagram participant U as 利用者 participant V as BackupSettingsSection participant B as BackupService participant S as PhotoArchiveStaging participant C as ModelContext U->>V: 「バックアップから復元」→ ファイルを選ぶ V->>B: readPackage（NSFileCoordinator で読む＝iCloud の写真を先に落とす） B->>B: decodeManifest → version 確認 → validate（写真名の検査・LR-015） B-->>V: manifest ＋ 欠けている写真の枚数 V-->>U: 確認アラート（件数・欠けた写真） U->>V: 「復元」 V->>B: restore(manifest, photosDirectory) B->>B: validate をもう一度 B->>S: begin（photos.staging を作る） B->>S: 写真を1枚ずつ staging へコピー（無いものは飛ばす） B->>C: 既存5モデルを1件ずつ delete（保存はまだ） B->>C: manifest から insert（無かった写真は記録から外す） B->>S: markSaved（staging に .db-saved の印） B->>C: save() alt 保存が失敗 B->>S: abort（staging を捨てる） B->>C: rollback() V-->>U: 「もとのデータはそのまま残っています」 else 保存が成功 B->>S: commit（staging → .incoming の rename がコミット点 → 本番と入れ替え） alt 入れ替えが失敗 B-->>V: photoSwapPending V-->>U: 「アプリを開き直すと写真が表示されます」 end V->>V: 下書きを消す・onboardingCompleted = true end

中断からの復旧（起動時）

アプリの起動時（LifeReviewApp.init）に毎回 ImageStore.recoverInterruptedRestore() → PhotoArchiveStaging.recover を呼ぶ。

起動時に残っていたもの意味処理
photos.staging（印なし）DB の保存より前に落ちた＝記録は復元前のままstaging を捨てる。本番の写真は触っていないので元どおり
photos.staging（.db-saved の印あり）DB の保存の直前か後に落ちた＝記録は新旧どちらか分からない本番の写真のうち staging に無いものを staging へ移してから切り替える（新旧どちらの記録でも写真を失わない）
photos.incomingコミット点は過ぎたが入れ替えの途中で落ちた入れ替え（本番 → .outgoing、.incoming → 本番）をやり切る
photos.outgoing入れ替え済みの古い写真消す

ビジネスルール

  • 復元は全置き換え。足し合わせ・選択復元はしない。必ず件数入りの確認を経由する。
  • 復元に失敗したら、元の記録も写真も1つも失わない。写真は staging に書き切ってから、DB の保存が成功した後で入れ替える。
  • パッケージに実体が無い写真は、復元全体を止めずに飛ばし、その写真の参照は記録から外す（実体の無い参照を残さない）。何枚欠けているかは確認の時点で知らせる。
  • 写真名に ../ や . / .. を含む（＝ファイル名1つでない）バックアップは、壊れているか細工されたものとして何も置き換えずに断る（LR-015）。
  • 復元の成功後は書きかけの振り返りを消す（別のデータに対する下書きを残さない）。
  • 「前回の書き出し」は、保存先に書き出せたときだけ更新する。

エラー処理

エラー原因対応
BackupError.unsupportedVersionmanifest の version が 2 でない何もせず「このバックアップの形式には対応していません。」
BackupError.corrupted写真名が安全でない／読み取りの結果が得られない何も置き換えず「壊れているため復元できません。いまの記録はそのまま残っています。」
デコード失敗など人生アルバムのバックアップでない・JSON が壊れている「このファイルは復元できません。」
復元中の失敗（コピー・保存）容量不足・保存の失敗などstaging を捨て rollback。「もとのデータはそのまま残っています。」
BackupError.photoSwapPendingDB は保存できたが写真の入れ替えだけ失敗復元は成功扱い。次の起動の recover が入れ替えを済ませる旨を表示

課題以前の作り直し方コミット
LR-001 復元の失敗で写真が全損「全消し → 書き戻し」。書き戻しや save で失敗すると SwiftData は rollback できても、削除済みの画像ファイルは戻らなかった新しい写真を staging に書き切り、DB 保存の成功後に rename で切り替える（PhotoArchiveStaging）。中断は起動時に後始末1e3fbfa
LR-002 メモリ超過1枚の JSON に全写真を base64 で詰めていた（書き出しも復元も全写真が一度にメモリへ）manifest.json と photos/ のパッケージに分け、写真はファイル単位でコピー・遅延読み出し。ピークは写真1枚ぶん1e3fbfa
LR-015 細工したバックアップで記録が全部消える写真名をそのまま信じていたため、../ を含む名前を戻すと、後で記録を消したときに画像ディレクトリの外（DB を含む）まで消えうるImageStore はファイル名1つだけを受け付ける。復元前に manifest を検査し、1件でも危ない名前があれば何も置き換えずに断る747f129
レビューでの追加修正iCloud の写真が落ちていないと「無い写真」として消える／保存途中の中断で写真がずれる／一括削除が rollback で戻らず、保存の失敗で元の記録が消えていたNSFileCoordinator で読む・欠けた枚数を確認に出す／.db-saved の印と photoSwapPending／1件ずつの削除に変更16c2621

実装メモ

  • 書き出しは BackupPackageDocument（FileDocument）。写真は FileWrapper(url:options: [])（.immediate なし＝遅延読み出し）で、書き出しの瞬間に全写真をメモリへ載せない。
  • 読み込みは FileDocument を使わない（パッケージ全体をメモリに載せるため）。fileImporter の URL からファイル単位で読む。セキュリティスコープは確認と復元の各回で開け閉めする。
  • context.delete(model:) はストアへの一括削除で rollback が効かないため使わない。deleteAll は fetch して1件ずつ context.delete する。
  • ファイル名の日付は Date.ymd（"2026/9/20"・スラッシュ入り）を使わず %04d%02d%02d。
  • テスト: 細工したバックアップの拒否・現データの維持・削除の封じ込め・保存失敗時に元の記録が残ること など（LifeReviewTests/BackupTests.swift）。
