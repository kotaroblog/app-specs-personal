広告制御機能

Unity LevelPlay（バナー + インタースティシャル）／配信は App Store 版のみ

v3.1機能ID: CR-FEAT-AD2026-08-23 更新
現状: 広告は一切配信されていない。 2026-07-30 に AdMob アカウントが「無効なトラフィック」を理由に恒久的に無効化され、再審査請求も却下された。 その後 AppLovin MAX へ移行したが publisher アカウントの承認が下りなかったため、 2026-08-20 に Unity LevelPlay へ再移行した。 CHROMATIC は App Key と広告ユニットIDが未設定（空）のため、現時点では広告のリクエスト自体が発生しない。

再発防止の設計（最重要）

アカウント無効化の原因は、開発・TestFlight での検証中に本番の広告でインプレッションが発生していたことにある。 ネットワークを変えても自己クリック・視聴依頼の禁止という規約は同じであるため、 広告をロード・表示するのは App Store 配信版のみに限定した。

判定内容
AdEnvironment.isProduction App Store 配信版か。判定はApp Store レシートの種別（sandboxReceipt かどうか）で行う。TestFlight・Xcode から実機へ直接インストールした場合のレシートは sandboxReceipt になるため、ビルド構成の設定ミスでは判定が破れない
AdEnvironment.isAdDeliveryAvailable !appKey.isEmpty && isProduction（App Key が設定済み かつ App Store 配信版）のときだけ true。バナーの表示可否・全画面広告の呼び出し・SDK 初期化がこの値で分岐する。ATT ダイアログの表示はこの値では判定しない（2026-08-23 変更。後述の shouldRequestTracking を使う）
LevelPlay にも AdMob のような「テスト広告ID」の概念がない。 そのため開発中は「広告を出さない」方式を採用し、レイアウト確認は広告枠のプレースホルダで行う。 本番広告での目視確認は行わない。
具体的な App Key・広告ユニットIDは本仕様書には記載しない（コード側で管理する）。

インタースティシャル呼び出さない。ロードもしない同上

ATT（トラッキング許可）ダイアログ広告の配信可否とは分離（2026-08-23 変更）。App Key が設定済みなら審査ビルドでも表示する。App Key 未設定の現在は表示しない審査は sandbox 環境で実行されるため、配信可否で ATT をガードすると審査担当者に ATT が表示されず Guideline 2.1 でリジェクトされる。一方、広告を一切出さない版（App Key 未設定）で許可を求めると Guideline 5.1.2 の懸念が出る

ATT（トラッキング許可）ダイアログの表示条件（2026-08-23 変更）

問題: ATT の表示を AdEnvironment.isAdDeliveryAvailable でガードしていた。 この値は isProduction（App Store レシートが sandboxReceipt でないこと）を含む。 App Store の審査は TestFlight と同じ sandbox 環境で実行されるため、 審査担当者の手元では ATT ダイアログが原理的に表示されなかった。

実害: 2026-08-22、CHROMATIC 1.4.0(7) が iPadOS 26.6 の審査で Guideline 2.1 - Information Needed によりリジェクトされた。

対策: 広告の「配信可否」と ATT の「表示可否」を別の判定に分離した。

/// 広告の「配信」は App Store 版のみ（isAdDeliveryAvailable）に限定するが、
/// ATT ダイアログの「表示」は審査ビルドでも行わなければならない。
static var shouldRequestTracking: Bool { !appKey.isEmpty }
判定条件用途
isAdDeliveryAvailable!appKey.isEmpty && isProductionSDK 初期化・広告のロード・広告の表示
shouldRequestTracking!appKey.isEmptyATT ダイアログの表示
環境広告の配信ATT ダイアログ
App Store 配信版（App Key 設定済み）配信する表示する
審査ビルド / TestFlight（App Key 設定済み）配信しない表示する
DEBUG ビルド / シミュレーター（App Key 設定済み）配信しない表示する
App Key 未設定配信しない表示しない

App Key 未設定＝広告を一切出さない版では ATT を表示しない。 これにより「広告がないのにトラッキング許可を求める」Guideline 5.1.2 の懸念も同時に満たす。

プライバシーマニフェスト（PrivacyInfo.xcprivacy）の方針

NSPrivacyTracking: false ＋ NSPrivacyTrackingDomains はキーごと削除が正解。 誤って true に戻したり、ドメインを列挙したりしないこと。

  • NSPrivacyTracking: true かつ NSPrivacyTrackingDomains が空だと ITMS-91064 でリジェクトされる（2026-08-20 に3本同時被弾）
  • NSPrivacyTrackingDomains は申告ではなく実行時のブロックリスト。載せたドメインは ATT 非許可時に OS が通信ごと遮断する
  • Unity Ads は広告配信とトラッキングで同じドメインを使うため、載せると ATT を拒否したユーザーに広告が1本も出なくなる
  • トラッキングの申告は App Store Connect の App Privacy 側で行う

ATT の要求タイミング（CHROMATIC 固有）

  • shouldRequestTracking == true（App Key が設定済み）であること（〜2026-08-22 は isAdDeliveryAvailable で判定していた）
  • 3ゲーム完了後のゲームオーバー時（初回ゲームオーバーからの変更）
  • ステータスが notDetermined であること
  • 撮影モードでないこと

許可・非許可いずれでも広告配信は可能で、非許可時は非パーソナライズ広告になる。

ビジネスルール

  • 広告のロード・表示は App Store 配信版でのみ行う。DEBUG・シミュレーター・TestFlight では一切リクエストしない
  • App Key または広告ユニットIDが未設定の間は、広告に関わる処理を一切実行しない（安全側の既定）。CHROMATIC は現在この状態
  • SDK の初期化完了前は広告をロードしない（LevelPlay は初期化前の loadAd() が失敗するため）
  • ATT ダイアログの表示は広告の配信可否と分離する。shouldRequestTracking = !appKey.isEmpty で判定し、審査ビルド（sandbox 環境）でも表示する。App Key 未設定の版では表示しない
  • PrivacyInfo.xcprivacy は NSPrivacyTracking: false ＋ NSPrivacyTrackingDomains キーごと削除の構成を維持する
  • プレミアム購入者には広告を表示しない。今後広告を再開した場合も表示しない（購入時の保証）
  • 全画面広告には必ず表示間隔（4ゲームに1回・最低90秒）を設ける
  • バナーはアダプティブサイズの高さをそのまま使い、固定値でクリップしない（広告の一部が隠れるとポリシー違反）
  • 広告をボタンやタップ導線に隣接させない（誤クリック誘発の禁止）
